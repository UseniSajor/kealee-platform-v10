# Professional and Homeowner Boundary

## Decision

White-label operating systems are sold to professional organizations. The
tenant is the professional company. A homeowner is a customer/project
participant, not a tenant administrator and not automatically a member of that
company.

This boundary is both a product decision and a security boundary.

## Audience classification

| Audience | Identity relationship | Primary surface | Authorization root |
| --- | --- | --- | --- |
| Kealee platform operator | Platform role | `apps/os-admin` | Explicit platform admin role |
| Tenant owner/admin | Active `OrgMember` | Branded professional admin | Membership + tenant role + entitlement |
| Tenant professional | Active `OrgMember` | Professional portals/modules | Membership + role + project/module permission |
| Homeowner/customer | Customer/project relationship | `apps/portal-owner` | Explicit project/property invitation or ownership relationship |
| External professional collaborator | Time/scope-limited collaboration | Professional collaboration surface | Explicit engagement/project grant, not implicit tenant membership |

## Separation rules

1. Creating a homeowner invitation must never create `OrgMember`.
2. A professional tenant invitation must explicitly declare the tenant role and
   be accepted before professional access is active.
3. A user who is both a homeowner and a professional has two contexts. The UI
   must require a deliberate context switch and the server must independently
   verify each request.
4. Homeowner endpoints cannot accept tenant-administration roles or module
   entitlements as substitutes for project access.
5. Professional endpoints cannot treat a homeowner's project access as tenant
   membership.
6. Tenant administrators may access homeowner/customer data only when the data
   belongs to a project or engagement assigned to their organization and their
   role permits the operation.
7. A tenant administrator cannot export or search global homeowner identities.
8. A marketplace relationship is represented by an engagement, opportunity,
   order, contract, or project record. It does not merge accounts or tenants.
9. Branding may cross the boundary; administration may not. A homeowner can see
   the professional's logo/colors on a project without gaining brand controls.
10. Usage generated by homeowner actions inside a professional's branded
    project is attributed to the professional tenant when the plan defines it.

## Recommended route boundaries

The exact route version may change, but separation should remain visible:

```text
/api/platform/white-label/*       Kealee operators only
/api/tenant/*                     Active professional tenant context
/api/professional/*               Professional role/project context
/api/homeowner/*                  Homeowner project/customer context
/api/marketplace/*                Audience-aware marketplace operations
```

A shared handler may serve multiple experiences only when its authorization
policy explicitly covers every audience and has tests for each branch.

## Recommended application boundaries

- `apps/os-admin`: Kealee platform management only.
- `apps/portal-contractor`, `apps/portal-developer`, and professional modules:
  tenant professional experiences.
- `apps/portal-owner`: homeowner/customer experience. The term `owner` here
  must not be interpreted as tenant owner.
- `apps/m-marketplace`: shared discovery/transaction surface with explicit
  audience-aware authorization.
- `apps/web-main`: public acquisition and unauthenticated informational flows.

Shared design-system components are encouraged. Shared authorization decisions
without explicit audience policy are not.

## Data classification

| Data | Owner/controller in platform terms | Homeowner visibility | Professional visibility |
| --- | --- | --- | --- |
| Tenant branding, plan, entitlements | Professional `Org` | Read-only presentation where relevant | Admin by authorized tenant roles |
| Homeowner profile | Individual/customer domain | Own profile | Minimum fields needed for assigned engagement |
| Project files and messages | Project/engagement | Explicitly shared subset | Assigned tenant roles |
| Professional rules, pricing assumptions, internal reports | Professional `Org` | Never unless intentionally published | Authorized tenant roles |
| Marketplace listing | Publishing professional/org | Public/marketplace fields | Publisher administration |
| Billing/usage for white-label license | Professional `Org` | Never | Authorized tenant billing roles |
| Homeowner payment/order | Customer order/project | Own order | Assigned professional visibility as contract permits |

## Context-switch behavior

For dual-audience users:

- display the active context prominently;
- issue or persist an explicit selected context;
- never select the first membership silently;
- clear tenant-only caches on context change;
- ensure deep links resolve to an authorized context or fail closed;
- record privileged context changes when they affect administration.

## Required test cases

- Homeowner with a project invitation cannot list tenant members.
- Homeowner cannot load white-label profile editing, plan, usage, domains, or
  integration credentials.
- Tenant admin cannot access an unrelated homeowner project.
- Tenant admin can access an assigned project's permitted customer fields.
- Dual-role user cannot reuse a homeowner session context for tenant admin API.
- Dual-role user cannot reuse tenant context to access an unrelated personal
  project.
- Removing project access revokes homeowner visibility without changing any
  professional memberships.
- Removing professional membership revokes tenant access without deleting the
  user's homeowner account or projects.
- Marketplace order/engagement grants only the documented relationship scope.
- Support impersonation never converts a homeowner into an organization member.
